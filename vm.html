[ VM ]// virtualization & lab building

Virtual machines.

A virtual machine is a whole computer running as software inside your real one — its own OS, disk, RAM and network, fully sandboxed. It is the single most important tool in a hacker's kit: a place to break things, detonate malware, and rebuild in seconds. This is the deep dive.

[ 01 ]// what is a virtual machine

Your physical computer — the host — has real hardware: a CPU, RAM, a disk, a network card. Virtualization is a thin layer of software called a hypervisor that slices those real resources into isolated virtual ones, and hands each slice to a guest operating system that believes it is running on its own dedicated machine.

The guest can't tell the difference. It boots a real OS (Linux, Windows, BSD), installs software, gets an IP address, and crashes or gets infected — all without ever touching your host. When you close the VM, that entire computer collapses back into a single file on your disk. Spin it up again and it's exactly where you left it.

Host

The real, physical machine and the software running directly on it. The host owns the hardware and runs the hypervisor.

Guest

The virtual computer running inside the host. Each guest has its own virtual CPU, RAM, disk and NIC, and its own independent OS.

Hypervisor

The referee. It allocates real hardware to guests, keeps them isolated from each other, and intercepts privileged instructions.

Virtual disk

A single file (.vdi, .vmdk, .vhdx, .qcow2) that is the guest's entire hard drive. Copy it = clone the machine.

Why bother? Isolation. A VM is a blast radius of exactly zero for your real data. Test a sketchy tool, open a suspicious file, run ransomware on purpose — then throw the VM away. It's also reproducible: the same VM file behaves identically on any machine.

[ 04 ]// how resources get virtualized

CPU

Modern CPUs have hardware virtualization (Intel VT-x, AMD-V) that lets guest code run almost natively. You assign a guest vCPUs (virtual cores); the hypervisor schedules them onto real cores. If your VMs won't boot 64-bit OSes, virtualization is usually disabled in the BIOS.

RAM

Each guest gets a fixed slice of RAM that's carved out of the host while it runs. Over-allocating (giving VMs more RAM than you physically have) leads to swapping and crawling performance. Techniques like ballooning let the hypervisor reclaim idle guest memory.

Disk

The guest's drive is a file on the host. Dynamically-allocated disks grow as data is written (a 50 GB disk might only use 8 GB on disk); fixed disks reserve all space upfront for speed. Formats: VDI (VirtualBox), VMDK (VMware), VHDX (Hyper-V), QCOW2 (QEMU/KVM).

Network & devices

A virtual NIC connects the guest to a virtual switch. USB, GPU, sound and clipboard can be passed through too. Guest additions / tools are drivers you install in the guest for smooth resizing, shared folders and copy-paste.

[ 05 ]// snapshots, clones & the magic undo button

A snapshot freezes the exact state of a VM — disk, RAM, settings — at a moment in time. Keep working; if anything breaks, revert and you're instantly back as if it never happened. This is the superpower that makes VMs the perfect place to experiment.

  • Snapshot before anything risky — installing malware, a kernel update, a config you don't trust.
  • Copy-on-write: after a snapshot, new writes go to a separate delta file, so the original state is preserved cheaply.
  • Clones duplicate a whole VM. A linked clone shares the base disk (fast, small); a full clone is independent.
  • Golden image: set up a clean Kali once, snapshot it, and revert to that pristine state for every new engagement.
Don't hoard snapshots. Long chains of snapshots slow a VM down and can corrupt if mismanaged. Snapshot, do your thing, then either commit or revert — don't keep 30 of them forever.

[ 07 ]// why hackers live in VMs

Malware detonation

Run real malware on purpose in an isolated VM, watch what it does (files, registry, network), then revert. The host never gets touched. Use an Internal or Host-only network so it can't phone home or spread.

Sandboxing the unknown

Opening a suspicious attachment, testing a cracked tool, visiting a sketchy site — do it in a throwaway VM. Worst case, you delete the VM.

Isolated practice labs

Attacking machines you don't own is illegal. A VM lab gives you your own vulnerable targets to legally practice exploitation, pivoting and privilege escalation.

Clean, reproducible state

Every engagement starts from an identical snapshot. No leftover tools, no contaminated evidence, no "it worked on my machine."

[ 08 ]// build your first hacking lab

A classic starter lab is one attacker and one or more victims on a private network with no route to the internet or your real LAN. Here's the blueprint:

  • Hypervisor: install VirtualBox (free) or VMware Workstation Player.
  • Attacker: Kali Linux or ParrotOS — comes loaded with the tooling.
  • Targets: Metasploitable 2/3, DVWA, OWASP Juice Shop, or VulnHub boxes — intentionally vulnerable on purpose.
  • Network: put every VM on the same Host-only or Internal network so the lab is sealed off.
  • Snapshot each VM in its clean state before you start, so you can reset after you wreck them.
Golden rule: never point real attacks at machines or networks you don't own and have written permission to test. Keep the lab isolated — that's what the network mode is for.

[ 10 ]// limits, risks & gotchas
  • VM escape: rare but real bugs let code break out of a guest into the host. Keep your hypervisor patched; never assume a VM is a perfect prison.
  • VM-aware malware: sophisticated samples detect they're in a VM (checking drivers, MAC prefixes, timing) and go dormant to dodge analysis. Analysts harden their VMs to hide the tells.
  • Performance overhead: VMs share your real CPU/RAM/disk. Running several at once needs decent hardware (16 GB+ RAM helps a lot).
  • Nested virtualization (a VM inside a VM) works but is slow and needs explicit support.
  • Snapshots aren't backups: if the disk file is lost or corrupted, the snapshots go with it. Back up the VM files separately.

Key terms

  • Hypervisor — the virtualization layer.
  • Guest additions / VMware Tools — in-guest drivers.
  • vCPU — a virtual core assigned to a guest.
  • Passthrough — giving a guest direct access to real hardware (e.g. a GPU).
